# Agent Note: 永久移除会话

Status: implemented

[English](2026-10-25-permanent-session-removal.md) | 中文

## Problem

会话存储在产品内部没有任何空间回收路径。`WorkspaceRegistry.archiveSession` 只隐藏会话行，其 JSONL 目录仍无限期留在持久化根目录下，而该 seam 根本没有删除操作——剪枝已存储会话在文档里属于带外后端维护。想彻底删掉一段对话的用户只能趁宿主还握着写租约时手工删文件，既无法保证注册表成员关系、归档与置顶集合、后端缓存视图或其他进程的打开句柄保持一致，产品也需要一个从 Web 侧栏经 Remote API 一直贯通到任意持久化后端的统一「删除这个会话」答案，同时不能静默丢弃用户以为只是被隐藏的数据。

## Decision

删除是由分层拥有的硬删除，且只有人类能触发。

- **seam 暴露 `remove(id, { signal? })`。** 它永久移除一个已存储会话的持久产物，并将其从本后端的可见性中释放：成功之后 `stat` 返回 `undefined`、`list` 不再包含该会话、`open` 以不存在拒绝。未知 id 不是错误——其他进程可能早已移除它——需要存在性语义的调用方先用 `stat` 检查。本进程持有打开句柄时，移除会以 `SessionAlreadyOwnedError` 拒绝；调用方必须先完成 dispose（资源释放），这让删除不必与活跃写入方竞速，而不是去定义二者之间的合并语义。跨进程可见性遵循各提供方的新鲜度规则；随产品交付的 JSONL 后端在下一次 `stat`/`list` 时刷新元数据读取。
- **JSONL 后端直接删除会话目录。** 保留的全部代际随之消失，包括释放时刻意留在原地的 `session.lock` 文件。对该 id 的缓存解码与准备一并清除。未实体化的已创建会话可干净删除、不留痕迹。另一个进程的内核租约不阻止删除：锁随其持有者消亡，而该持有者之后的操作只会报告会话不存在。
- **`WorkspaceRegistry.deleteSession(sessionId, { stopActivity? })` 是归档的可逆性取反镜像。** 它与归档跑在同一条串行化操作链上，执行同样的存在性检查与 `workspace/session-activity` waterfall 拒绝——除非 `stopActivity` 先派发 `workspace/session-stop`——随后销毁实时 Agent（智能体）、经由 `sessionPersistence.remove` 移除日志，并把该 id 从每个 workspace 的 `sessionIds` 列表以及归档与置顶集合中剔除。它的写入在同一链槽提交，因此并发的 attach 不可能在删除之后再把这个 id 加回来。
- **删除绝不级联。** fork 子代与 subagent 子孙保留各自的日志和悬空的 `parentSession` header 引用——这是血缘读取方本来就容忍的展示元数据，因为今天外部手工删除目录造成的正是同一状态。级联意味着一次确认点击就静默摧毁用户从未点名的对话。
- **只有一个远程契约：`session.delete { sessionId, stopActivity? } -> { deleted: true }`，Client 面为 `sessions.delete(...)`。** 控制器会解析冷 Session，把准入与拆卸委托给注册表，并像其他按地址寻址的方法一样把该 action 登记在 `session` 资源种类之下。
- **仅限用户发起，拒绝即确认。** 没有任何 agent 工具能执行删除，这与 workspace 删除政策一致：破坏性文件系统动作必须单独命名并获得明确确认。侧栏把 `delete` 注册进 `sidebar.workspaces.session.menu.item` 的 order 420——位于 Archive（400）与 Copy Session ID（450）之间——其对话框写明永久性。运行中的会话被拒绝后打开「停止并删除」，复用停止并归档对话框的形状：宿主列出将要停止的内容，取消则一切不变，拿不准时文档引导用户选择仍然可逆的归档。

## Alternatives considered

**回收站目录式软删除加保留期** —— 在一次清扫之前什么空间都不回收，把归档的职责重复了一遍还添了一段用户必须理解的隐形生命周期；可逆性已经归归档所有，而一个能在应用内反悔的删除恰恰制造了硬删除要消除的歧义。磁盘回收与产品简单性都要求目录在确认那一刻消失。

**级联删除 fork 子代与 subagent 子孙** —— 血缘字段确实让子孙可发现，但它们是用户没有选中的独立对话；一起删除等于对用户数据搞突然袭击，而保留它们分文不花，因为父引用会退化为展示元数据。这与「移除 workspace 注册记录绝不删除其会话」的既有规则同构。

**在 deleteSession 内部隐式停止** —— 越过正在运行的工作直接删除省掉了一个对话框，却摧毁了没人要求结束的轮次，违背归档的先例：拒绝本身就是确认，停止只在显式请求时发生。`stopActivity` 让这个选择保持用户可见。

**提供一个 agent 可调用的删除工具** —— agent 会销毁自己看不全的会话历史；其他对已存储用户数据的破坏性控制（workspace 移除、批准范围之外的文件删除）都由人类把关，插件惯例也要求不可逆动作获得人类确认。

**让持久化后端独自拥有删除** —— 后端认识文件，却不认识注册表成员关系、归档与置顶集合或实时 Agent；少了注册表这一层，被删会话会以幽灵成员身份滞留在持久 workspace 列表和侧栏投影里。

## Consequences

一次确认的删除立即且永久地释放磁盘：UI、API 与存储层都没有撤销路径，因此对话框写明永久性，文档把犹豫的用户引向归档。被删会话会在子代里留下悬空的 `parentSession` 引用，`session-query` 与导出消费方必须把缺失父级当作常态处理。注册表清理按链槽原子完成，但日志移除与注册表写入是两个步骤：两者之间崩溃要么留下一个孤立日志目录（重试时再次删除），要么留下有列表无存储的 id——这与外部手工删除早已产生的分叉相同，靠现有的读取时成员过滤消化。其他进程通过下一次元数据读取惰性感知删除，没有任何机制主动失效它们的缓存。后端实现方从此多出一个由共享契约套件固定的可观察方法；删除代价高昂的第三方提供方继承同样的「句柄打开即拒绝」义务。
